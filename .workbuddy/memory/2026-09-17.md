# 2026-09-17

## 修复近邻宝短信解析（用户实测反馈）

用户反馈这条短信有三个问题：

```
【近邻宝】凭「9911-9276」到学生公寓西侧10号柜，五日签收L18取件
```

1. 认不出是近邻宝
2. 没提取柜体（10号柜）
3. 没提取格口（L18）

### 先用临时测试看真实解析结果（好用的套路）

写 `tests/_tmp.test.ts`，让测试**自己用 `fs.writeFileSync` 写 UTF-8 结果文件**，再用 Read 读 ——
绕开 Windows 终端中文乱码（vitest 的中文输出经 GBK 控制台会糊成一片）。

改前结果：

```json
{ "pickupCode": "9911-9276", "stationName": "学生公寓西侧10号柜" }
```

→ 驿站名里没有「近邻宝」（品牌只在开头的 `【】` 签名里），且 boxNo 为空。

### 根因

- 「到 X 取件」结构只看正文，抓不到 `【近邻宝】` 这个发件方签名。
- `CABINET_REGEX` = `([0-9A-Za-z]{1,3})柜`，只认「B柜」这种**字母在前**的写法，抓不到「10号柜」（数字在前）。
- 格口 `L18` 写在「签收…取件」之间，没有任何规则覆盖。

### 改动

- `src/parser/rules.ts` 新增三条：
  - `CABINET_NO_REGEX = /(\d{1,3})\s*号柜/` —— 匹配「10号柜」
  - `LOCKER_SLOT_REGEX = /(?:签收|格口|格子|柜门|箱门)\s*([A-Za-z]{1,2}\d{1,4})/` —— 匹配「签收L18」
  - `SENDER_TAG_CAPTURE_REGEX = /[【\[]\s*([^】\]]{2,12}?)\s*[】\]]/` —— 抓发件方签名
- `src/parser/engine.ts`：新增 2b 段（签名存进 `senderTag`）+ 4c 段（柜体&格口拼进 `boxNo`）
- `src/types/index.ts`：`ParsedPackage` 新增 `senderTag?: string`（不进 DB，无需走 Package 那份核对清单）
- `src/services/stationMatch.ts`：`resolveFixedStationId(stationName, courierCompany, senderTag)`，
  判定顺序 **驿站名 → 签名 → 快递公司 → 兜底菜鸟**
- `app/import.tsx`：两处调用补上第三个参数

### ⚠️ 中途踩的坑（值得记住）

**第一版我把签名直接拼进了 `stationName`**（变成「近邻宝 学生公寓西侧10号柜」），
结果**6 个旧测试全挂** —— 断言精确匹配的 stationName 被污染，冒出「邮政驿站 中国邮政」
「美团智能外卖柜 民族丰台校区…」这类噪音。

**教训：不要为了让匹配通过而去污染「语义上应保持干净」的字段。** 正确做法是**新增一个字段承载额外线索**，
让消费方自己决定优先级。
> 也再次印证：**改解析规则后必须跑全量测试** —— 旧用例就是回归网。
